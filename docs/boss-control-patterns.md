# 베스퍼 이후 제어스킬 후보와 내부 대응 구간

현행 기르타블리르 상태(2026-09-20): OFF 실험과 기준 조합 성공 확인을 종료하고 진입RMB250ms·1~3타SPACE각400ms 및 새 대표 영상을 웹에 반영했다. 아래 외부 영상·초기 후보는 조사 이력이다. [현행 채택값과 반례](experiments/girtablullu-control-skill.md)를 우선한다.

**초기 조사 이력 — 2026-09-18:** 사용자 요청으로 설치된 게임 설정과 공개 명칭·설명을 대조했다. 당시 다음 대상으로 사용자가 확인한 **기르타블리르·퇴행 변종(Girtablullu - Stagnant Aberrant)**을 선택했다. 내부 식별자는 `GirReborn`이며 일반 `Girtablu`, 융합형 `Girtablu_HC`와 구별한다. 이 초기 정적 조사에서는 실제 게임 입력·새 실험·녹화 판독을 수행하지 않았다.

원본 위치·번들 offset·객체 ID·해시·원문 필드·계산은 [기계 근거](evidence/boss-control-patterns-20260918.json)에 보존했다. 게임 `.blk`는 읽기만 했다. 기존 능력 레지스트리의 10,054개 이름을 현재 설치본 카탈로그로 찾아 조사했으며, 이름이 존재한다는 사실만으로 모든 전투에서 해당 동작이 발동한다고 판단하지 않는다.

## 현재 작업 순서 — 2026-09-21

베스퍼와 기르타블리르·퇴행 변종은 실험·대표 영상·웹 반영 및 사용자 수용을 마쳤다. 기르타블리르의 OFF39회·기준 조합 성공·채택 구간은 [현행 보고서](experiments/girtablullu-control-skill.md)를 따른다. 아래 기르타블리르 외부 영상 후보와 첫 묶음은 완료한 준비 과정의 이력이며 재실행 지시가 아니다.

현재 진행은 [README](../README.md#현재-단계--2026-09-21)를 따른다. 쿠사리쿠의 웹 반영·검증·정리와 환영의 화살 유닛 사전·외부·내부 조사를 마쳤다. 환영의 화살 유닛은 아리아→남궁우→수나, 시작 아리아이며 [현행 조사](experiments/arrow-unit-control-skill.md)의 수동7개·자동20회와 대표 녹화2개를 근거로 기본진입RMB+Space4를 웹에 반영한다. 대체 입력과 겹침 표시는 별도 논의 중이다.

공개 순서와 환영의 화살 유닛·진입 Space·마지막 타 RMB 대응의 후속 채택 조건은 [제품 합의](product.md#후속-보스-확장-운영--2026-09-19)를 따른다.

## Pre와 Combo의 공통 해석 — 2026-09-21

베스퍼·기르타블리르·퇴행 변종·쿠사리쿠에서 확인한 제어스킬은 **Pre에서 진입 회피, Combo에서 진입 이후 1~n타**로 대응한다. 이는 대응 순서의 공통 명명이며, Pre 상태 전체가 한 번의 진입 회피만으로 구성된다는 뜻은 아니다. 보스 동작은 아래 명칭으로 설명하고, RMB·Space 같은 대응 입력은 따로 표기한다. ‘진입 회피’는 단계의 명칭이며 RMB만 가능한 입력이라는 뜻은 아니다.

| 확인한 패턴 | Pre | Combo | 타수 확인 근거 |
|---|---|---|---|
| 베스퍼 Execute_02 | 진입 회피 | 1~4타 | 내부 구현과 완료한 로컬 실험 |
| 베스퍼 Execute_01 | 진입 회피 | 1~5타 | 내부 구현과 완료한 로컬 실험 |
| 기르타블리르·퇴행 변종 | 진입 회피 | 1~3타 | 내부 구현과 완료한 로컬 실험 |
| 쿠사리쿠 | 진입 회피 | 1~4타 | 내부 Pre/Combo 구분과 사용자의 직접 타수 확인 |

이 대응 관계는 이후 조사에서 재사용하며, 위 패턴의 진입·타수 구분을 다시 미확인 질문으로 돌리지 않는다. 새 패턴에서도 같은 Execute 구조를 확인하면 이 해석을 출발점으로 삼되, Combo 안의 사건·modifier 개수만으로 실제 타수나 물리 입력 수를 확정하지 않는다. 단계 구분과 시간 원점은 별개다. 베스퍼 Execute_01은 같은 클립의 Combo 전환 offset280을 사용하므로, Pre/Combo라는 이름만 보고 좌표가 0으로 초기화된다고 해석하거나 내부 좌표를 입력 ms로 환산하지 않는다. 시간 원점의 기존 근거는 [연구 기록](experiments/research-history.md#execute_01--현재-근거로-가능한-판단)을 따른다.

공통으로 재사용하는 것은 **진입/후속이라는 역할**이며 literal 상태명은 필수 조건이 아니다. 환영의 화살 유닛은 `Attack_09_01`이 진입, `_02`~`_05`가 후속 역할이다. 내부 다섯 상태와 외부 시연의 첫 대응·후속2·3·마지막 안내를 교차했지만, 9월22일 수동 영상에서 아리아→남궁우→수나→아리아→남궁우와 진입RMB+후속Space4의 오버레이 시각을 확인했다. 물리 입력 지연·자동 성공 경계는 아직 미측정이다. 위 완료 패턴의 해석을 바꾸거나 새 상태명을 Pre/Combo로 개명하지 않는다.

쿠사리쿠는 같은 Pre 상태에 준비 투사체 호출과 후반 진입 회피 감지가 함께 설정되어 있다. 따라서 **준비 대응 → 진입 회피 → 1~4타**로 설명한다. 준비 대응은 플레이어의 대응을 구분하는 이름이며 게임의 별도 `Preparation` 상태명이나 Combo0타가 아니다. 실행기의 `준비 회피1·2`는 선택한 성공 영상 경로의 RMB 두 번, 방향 이동 라벨은 그 입력의 역할을 뜻한다. 보스의 공식 공격명·투사체 수를 뜻하지 않는다. 내부 연결과 남은 한계는 아래 준비 공격 구현 절을 따른다.

## 마지막 타 회피와 QTE의 공통 해석 — 2026-09-21

**제어스킬의 마지막 타를 RMB로 극한 회피하면 QTE로 이어진다. 회피지원도 같은 QTE로 이어진다.** 제어스킬 대응의 공통 규칙으로 채택하며 보스마다 다시 미확인 질문으로 돌리지 않는다. QTE는 마지막 타 대응의 결과이며 추가 보스 타수로 세지 않는다.

기존 후보의 실행 관리자 전체와 베스퍼 두 패턴을 대조했다. 표준 제어스킬 14개 경로 모두 마지막 처리의 `OnAdded`에서 회피 감지를 붙이고, `OnDodgeSuccess`에서 직접 또는 별도 관리자를 거쳐 `StartRealtimeQTEAction`의 공통 설정 `Common_Monsterr_Execute_RealTimeQTE`로 연결된다. `EvadeAid`는 지연 분기로 같은 설정을 사용한다.

| 내부 구현 방식 | 확인한 실행 관리자 |
|---|---|
| 같은 관리자에서 공통 QTE 시작 | GirReborn, Girtablu, Larval, Mutant 일반·HC, Stalker, SymbioticEtherealSinner, Vessel Execute02 — 8개 |
| 별도 QTE 관리자를 호출해 공통 QTE 시작 | GraymaneCenturion, ObsoleteAndroid, Vessel 일반·HC, Vesper Execute_01·02 — 6개 |

출처·해시·연결 경로는 [기계 근거](evidence/boss-control-patterns-20260918.json)의 `qteCommonReview`에 통합했다. [게임 내 제어스킬 튜토리얼 전재](https://zenless-zone-zero.fandom.com/wiki/Tutorial/Control_Skills)도 마지막 타의 극한 회피·회피지원에 따른 정밀 반격을 공통으로 설명한다. 초기 목록에서 이름만으로 후보에 포함한 `IsoldetheDefiler_Execute_Manager`는 잡기 피격으로 시작하고 위 마지막 회피→QTE 연결이 없는 별도 설정이므로 표준 제어스킬 확인 목록에서 제외했다. 이를 공통 규칙의 미해결 예외로 남기지 않는다.

제품에서 마지막 타 RMB 대응을 추가할지는 **초기 커뮤니티 공개 후 피드백으로 판단**한다. 기본 대응의 마지막 Space 성공 폭을 RMB에 복사하지 않는다.

## 쿠사리쿠 — 서비스 채택 및 종료

사용자 수동 WASD와 자동 전투 입력의 무피격·완벽 대응 대표를 채택했다. 준비 회피·이동은 비채점 영상 안내이고 진입+4타의 다섯 구간을 연습한다. 현행 수치·조건·19영상과49회에서 남길 결론·01111 해석은 [쿠사리쿠 정본](experiments/kusarikku-control-skill.md), 영상 원점과 클립은 [서비스 미디어](evidence/service-media-20260920.json), 내부 구조의 출처는 [정적 근거](evidence/kusarikku-control-20260921.json)를 따른다. 완료한 후보·준비 배포 절차와 중복 영상별 이력은 제거했다. 새 반례 없이 종료한 구간을 다시 탐색하지 않는다.

## 기르타블리르·퇴행 변종: 진입 + 3타

아래 숫자는 **각 애니메이션 상태의 내부 좌표**다. `Pre`와 `Combo`는 별도 원점이며, 문구 감지 후 ms나 영상 프레임으로 바꾸지 않았다. 폭은 `끝−시작`이다.

| 역할 | 상태 | 시작 | 끝 | 폭 | 의미 |
|---|---|---:|---:|---:|---|
| 진입 회피 성공 수신 | `Attack_Execute_01_Pre` | 199 | 230 | **31** | `OnDodgeSuccess` 등 성공 이벤트를 받아 진입 대응 결과를 처리 |
| 진입의 지원·회피 태그 | 같은 Pre | 199 | 229 | **30** | HeavyParry / Evade / Switch 태그 설정; 위 성공 수신과 다른 층 |
| 1타 지원 | `Attack_Execute_01_Combo` | 18 | 48 | **30** | 패링·회피지원·교대 태그 |
| 2타 지원 | 같은 Combo | 70 | 100 | **30** | 같은 계열 |
| 3타 지원 | 같은 Combo | 134 | 164 | **30** | 같은 계열 |
| 마지막 반격 성공 처리 | 같은 Combo | 133 | 168 | **35** | `Execute_ParryHit_Modifier`; 3타 입력 폭을35로 바꾸는 근거가 아님 |

#### 베스퍼에 먼저 되적용한 방법

지원의 위치는 내부 공격 좌표 대신 **입력 표시와 화면 반응의 경험적 관계**로 추정했다. 보존 기준 영상9타에서 `반응 좌표 = 촬영 기준 입력 + (반응 프레임−입력 표시 프레임)/60`이다. 표시 차이는100–150ms, 중앙값116.7ms다. 채택한 늦은 끝에서 그 기준 반응을 뺀 값은+33.3~+100ms, 중앙값+66.7ms다. 따라서 비교용 식은 `대표 입력 ≈ 외부 반응−116.7ms`, `늦은 끝 ≈ 외부 반응+66.7ms`, `이른 끝 = 늦은 끝−폭 후보`로 두었다. 실제 제안값은50ms로 반올림했다.

이것은 보편적인 입력 지연이나 늦은 판정 법칙이 아니다. **베스퍼 촬영 입력은 이미 선택 구간의 안쪽에서 골랐으므로 이 관계에는 그 선택의 영향이 있다.** 외부 플레이어의 성공 입력도 비슷한 상대 위치였다는 조건을 붙인다. 기준 반응 이후의 늦은 끝은 다른 시도의 가능한 입력을 같은 기준 화면에 놓은 값이며, 같은 회차에서 이미 끝난 대응을 뒤늦게 입력한다는 뜻이 아니다. 외부 성공 한 점을 구간의 중앙으로 증명하지 않는다.

#### 첫 실험 묶음 — 2026-09-20 교정

아래는 완료한 기르타블리르 실험 준비의 역사적 설계다. 현재 채택값과 종료 결과는 [현행 보고서](experiments/girtablullu-control-skill.md)를 따른다.

**결정할 질문:** 예측 대표값에서 로컬의 정상 경로가 성립하는가. 성립하면 각 동작의 이른/늦은 후보가 다른 동작을 기준값으로 둔 조건에서 성공하며, 최종 선택 구간의 대표 교차 조합에서도 사용할 수 있는가. 위 외부 성공 경로·후보와 최신 베스퍼의 키·선행 조건별 결과를 함께 사용한다.

**비교 조건:** 각 보스의 대표 파티를 사용하고 같은 실험 묶음 안에서 조건을 고정한다. 사용자 로컬 녹화의 레미엘→벨리나→아리아·진입 아리아로 진행한다. 현재 예약 후보와 실제 첫 묶음은 [로컬 분석](experiments/girtablullu-control-skill.md)을 따른다. 아래 외부 앵커 숫자는 과거 예측이며 직접 실행하지 않는다. 실제 지원 종류·교대 순서를 연결하고 PowerStruggle 분기는 구분한다. 보스 형태·모드·파티·키 경로·화면·감지 설정은 묶음 안에서 고정한다. 키 차이의 전수 비교를 시작 조건으로 추가하지 않는다.

**녹화:** 구간 결정은 OFF를 기본으로 한다. ON은 문구 출현·감지·입력·반응 연결을 판독할 때 필요한 장면에 사용한다. ON 실패만으로 OFF 구간을 줄이지 않으며, ON5회→OFF1회 또는 보스마다 ON/OFF 대조를 의무 절차로 두지 않는다.

**기준 실패 시:** 진입 실패면 진입의 더 이른 대표 후보3.90초와 나머지 대표값을 비교할 수 있다. 우선3.90–4.10과 대안3.80–3.95는3.90–3.95에서 겹치므로 이 재시도 성공만으로150ms 대안 폭을 식별하지 않는다. 지원 실패면 성공한 앞부분을 유지하고 해당 입력의 위치·감지·교대 경로부터 검토한다. 실패한 기준을 둔 채 양끝·교차 비교를 계속하지 않는다. 선행 실패 뒤 결과는 정상 경로의 폭 근거와 분리한다.

**교차 실패 시:** 해당 조건만 재확인하고 최초 실패 동작의 해당 끝을 기준점 쪽50ms로 옮겨 회복되는지 확인한다. 단발 실패나 체감으로 모든 폭을 일괄 축소하지 않는다. 기준 조합도 불안정하면 감지·조건 변동을 먼저 구별한다.

**종료/분기:** 기준과 필요한 개별 양끝·대표 교차 두 방향의 성공 근거와 반례 처리가 갖춰지면 구간 선택을 정리한다. 더 넓은 대안이나 모든 조합을 확인할 의무는 없다. 약6회는 한 번에 진행할 부담을 나누는 작업 단위이며 첫6회에 네 동작의 모든 끝과 교차 검증을 억지로 맞추지 않는다. 다음 묶음에는 미확인 끝과 판단을 바꾸는 실패 조건만 넘긴다. 성공률 보증이나 정확한 물리 경계 확정은 종료 조건이 아니다.

**실행 전에 연결할 최소 정보:** 실제 파티/키 경로와 로컬 문구 감지 원점이다. 로컬 장면 이동량을Δ, 그 문구 앵커에 대한 감지 시각을D라고 하면 예약값 후보는 `표의 시각 + Δ − D`다.Δ가 타별로 달라지면 공통 이동을 강제하지 않는다. 필요한 경우 한 번의 문구 전~결과 후 입력 표시/로그 구간으로 공통 이동인지 타별 경로 차이인지 구분한다. 이 관측은 위 후보를 만들기 위한 선행 조건이 아니며, 현재 표를 곧바로 실행 가능한 ms 설정으로 포장하지 않기 위한 연결이다. 2026-09-20 후속 승인으로 이 연결에 필요한 문구 감지·4동작 프로필 준비와 무입력 검증을 진행한다. 후보 프로필 생성만으로 감지·게임 성공 검증이 끝난 것으로 보지 않는다. 실제 입력은 사용자가 수행하며 서비스 판정은 성공 근거 확보 뒤 별도로 반영한다.

**9월19일 사전 조사의 검증 범위:** 저장 영상 판독, 디코딩 프레임/PTS와 산술·해시 확인이다. 실제 게임 입력은0이며 사용자 환경의 성공·녹화 영향·학습 효과는 미검증이다. 외부 원본은 이 checkout의 Git 제외 연구 폴더에 보존하고, Git에는 출처·관측 JSON과 역할별 대표 발췌만 남긴다. 외부 영상은 연구 참조이며 서비스용 영상으로 편입하지 않았다.

두 보스 모두 일부 공격에 `ErosionSkillBeginTag`가 활성화되면 일반30 대신 조건부35의 Evade/Switch 구간을 쓰는 별도 분기가 있다. `ZenkovErosion` 이름만 보고 이를 미아즈믹 변형 전체의 축소 규칙으로 해석하지 않는다. 이번에 읽은 장벽·광폭화 관리자에서는 일괄적으로 성공 폭을 줄이는 규칙을 확인하지 못했다. 모든 모드의 동적 보정을 배제했다는 뜻은 아니다.

## 앞뒤 간격과 첫 대응 위치의 비교 — 후속 점검

사용자가 지적한 첫 지원 시작18/34와 구간 간격을 함께 비교하도록 해석을 보완했다. 앞선 조사에서는 마나토·제인의 구간 원문을 확보했지만 **연속 구간 사이 간격을 체계적으로 계산·비교하지 않았다.** 아래는 보존한 원문으로 이번에 계산한 결과다. Erosion 조건부 분기를 일반 구간과 중복 집계하지 않았다.

| 보스·상태 | 첫 구간 시작(상태 좌표0 기준) | 대응 태그 구간 | 구간 사이 간격: 다음 시작−앞 끝 |
|---|---:|---|---|
| 기르타블리르 Combo | 18 | 18~48 → 70~100 → 134~164 | **22 / 34** |
| 베스퍼 Execute_02 Combo | 34 | 34~66 → 105~137 → 183~215 → 271~303 | **39 / 46 / 56** |
| 마나토 Attack_06 | 8 | 8~38 → 137~167 | **99** |
| 마나토 Attack_08 | 66 | 66~96 → 165~195 | **69** |
| 마나토 Attack_10 | 14 | 14~44 → 64~94 → 134~164 → 230~260 | **20 / 40 / 66** |
| 제인 Attack_07 | 34 | 34~64 → 109~139 | **45** |

마나토 Attack_10은 폭이 모두30인데 앞뒤 간격은20·40·66으로 달라져, 일정한 폭 위에 타별 시간 문맥이 영향을 준다는 가설을 살펴보기 좋은 사례다. 반면 Attack_06/08의 지원 태그 간격은99/69이므로 마나토 전체가 베스퍼보다 간격이 좁다고 결론 내리지 않는다.

첫 구간이 동작 시작 근처에 있는 사례도 많다. 마나토 Attack_01/02/06/07/10의 첫 시작은1/0/8/9/14, 제인 Attack_01_01/05/06은0/6/2다. 제인의 짧은 Parry_Hit0~10, Attack_ParryAssault0~9도 모두0에서 열린다. 설정상 짧은 폭이라는 관찰은 유지하되, 이것만으로 별도의 보스 난이도 규칙이라고 설명하지 않는다. **전환 직후 빠른 공격 때문에 앞쪽 대응 여유가 제한되는 구조인지** 함께 검토할 후보다. 폭을 의도적으로30에서 잘랐다는 구현이나 실제 전환 후 지연을 확인한 것은 아니다.

또한 ‘지원 태그 사이 간격’ 전체가 쉬는 시간은 아니다. 예를 들어:

- 마나토 Attack_06의 지원 구간은8~38과137~167이지만 공격 이벤트는39·70·100·120·168이다. 간격99 안에도 여러 공격이 있다.
- 제인 Attack_07의 지원 태그 간격은45지만 공격 이벤트는65·77·87·104·140이다. 중간 타격은12·10·17만큼 떨어져 있다.
- 제인 Attack_08의 공격 이벤트92·113·133·209·211은 간격21·20·76·2다. 이 수치는 지원 구간의 끝→시작 간격과 다른 값이며, 마지막2를 ‘2마다 반드시 새 입력’으로 해석하지 않는다. 투사체 그래프까지 포함한 전체 충돌 사건 목록도 아니다.

따라서 현재의 설명은 **대체로30 안팎인 보스 대응 설정 위에, 첫 대응까지의 여유·앞뒤 대응 간격·중간 공격·회피/패링 유지가 실제 입력 여유를 제한할 수 있다**이다. 사용자의 앞뒤 간격 가설은 중요한 설명 후보이며 단순 폭 비교보다 유용하다. 다만 체감 차이를 간격 하나로 확정하지 않는다. 서로 다른 상태의 좌표를 직접 빼서 Attack_01→02 같은 연결 간격을 만들지는 않았다.

## 서비스와 다음 작업에 반영할 판단

- 기르타블리르·퇴행 변종은 **진입 + 3타**의 고정 제어기 콘텐츠로 진행한다. 다른 기르타블리르 형태의 자료를 혼합하지 않는다.
- 기르타블리르의 짧은 앞뒤 간격을 고려해 실제 성공 폭은 타별로 선택한다. 베스퍼의450ms를 복사하지 않는다.
- 두 보스 모두 첫 대응 위치·앞뒤 구간 간격·중간 공격을 폭과 함께 비교한다. 제인의 짧은 구간도 동작 전환 문맥에서 해석한다. 둘 다 ‘보스 전체 난이도=내부 폭’ 한 숫자로 정리하지 않는다.
- 위 외부 영상 후보는 사전 조사 이력이다. 기르타블리르는 통합 실험기의 문구 감지·4동작 프로필로 로컬 감지·성공 구간·서비스 반영을 완료했다. 쿠사리쿠와 환영의 화살 유닛도 종료했으며 현행 구간·원점·해석 한계는 각 보스 보고서를 따른다. 새 보스도 기존 통합 도구를 사용하며 별도 보스 전용 프로그램을 만들지 않는다.
