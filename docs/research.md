# 구현에 사용할 연구 근거

이 문서는 재사용할 해석·반례와 실험·평가 방법의 정본이다. 권한·담당 이전·문서 책임은 [AGENTS.md](../AGENTS.md), 제품 선택과 확장 조건은 [제품 합의](product.md), 현재 남은 결정은 [README](../README.md#현재-단계--2026-09-21)를 따른다. 날짜별 조사와 당시 다음 행동은 [연구·적용 평가 이력](experiments/research-history.md)으로 이동했다. 필요한 판단의 근거만 찾아 읽으며, 이력 전체를 재개의 필수 입력으로 삼지 않는다.

## 현재 판단과 종료 범위 — 2026-09-21

베스퍼·기르타블리르의 실험과 서비스 반영을 종료했다. EX01은 추가 완벽 대응 영상으로 교체한 뒤 사용자가 실제 게임과 거의 같은 체감이라고 수용했다. 영상별 전조·후속 진행 차이가 확인되었으나 모든 회차의 원인을 확정한 것은 아니다. 고정100ms 보정이나 엔진 전체 복원으로 이 불확실성을 메우지 않는다. [교체·비교 근거](experiments/vesper-latest-web-sync-20260920.md)와 [현행 미디어](evidence/service-media-20260920.json)를 따른다.

9월22일 쿠사리쿠와 환영의 화살 유닛도 서비스·도구 반영과 자료 정리를 마쳤다. 현행 값과 적용 조건은 각 보스 보고서를 따르며, 환영의 화살 유닛 진입 SPACE는 공개 후 수요에 따라 검토할 확장이다. 아래 실험 방법을 적용하려고 종료한 보스의 관측을 다시 수집하지 않는다.

실험 기준값·영상 입력 참조·서비스 양끝은 역할이 다르다. 기준값 선택과 대표 영상 채택은 [제품의 채택 기준](product.md#초기-구현값과-남은-제품-결정)에 따른다. 숫자 통일만을 위해 수용한 영상을 재녹화하지 않는다.

## 시간 원점과 관측의 적용 한계

일반 플레이의 구간 판단은 녹화OFF를 기본으로 한다. ON 실패만으로 공통 폭을 축소하지 않는다. 실제 문구 출현·실험기의 감지 기준·OS 입력 제출·녹화 표시·게임 수용·화면 반응을 서로 구별한다. API 지연이 작거나 캡처P95가 작아도 문구 대비 원점의 안정성을 증명하지는 못한다. OBS의UNKNOWN을OFF로 분류하는 운영 정책은 OBS 미실행을 직접 관측한 증거와 다르다. 원점이 바뀌면 숫자의 이동과 성공 폭 변화를 먼저 분리한다.

2026-09-21 HUD 대조에는 준비 점등83ms 전부터 키가 눌린 성공과, 노란 상태에서 입력해도 피격한 사례가 함께 있다. 고정 노란 준비 표시·지원 후 노란 펄스·키 표시는 서로 다른 사건이다. 점등→입력 간격을 성공창 경계나 공통 지연으로 채택하지 않는다. [로컬 관측](experiments/kusarikku-control-skill.md)을 따른다.

[같은 날 오후19개 수동 관측](experiments/kusarikku-control-skill.md)은 마지막 두 영상의 진입 전 보라색 전조가 기존 기준보다400~416.7ms 늦음을 확인했다. 입력의 늦은 성공을 허용창 확대로 오인하지 않는다. 준비 피해·진입 피해·후속 반응·게임 완벽 평가를 분리한다. 특히01111도 게임 완벽 대응이므로 최종 표시로11111을 복원하지 않는다. 투명 입력 표시 뒤의 방부/이펙트 오검출과W 검출 누락을 원본 인접 프레임으로 교정했으며, 문구가 이미 떠 있는 잘린 원점을 정상 최초 감지로 합치지 않는다.

사용자의 느린 LMB 설명에 따라 마지막 세 영상을 추가 정렬했다. 마지막 둘은26보다 첫 클릭→육안 문구가450/466.7ms, 육안 문구→십자가가500/533.3ms 더 길다. 클릭 다섯 누름의 총 간격은 오히려150/83.3ms 짧다. 문구→첫 준비 포털은1프레임 이내로 가깝고 이후 준비 피격/극한 회피가 갈라진다. 문구 이전의 공격 진행과 문구 이후 준비 대응을 구별하며, 감속 기여는 후보 원인으로 보존하고 고정 보정이나 단일 원인으로 채택하지 않는다.

정적 구간은 이벤트 수신 설정이며 물리 키 허용창과 동일하지 않다. [지원 입력의 코드 경로](experiments/research-history.md#지원-창과-실제-입력의-기본-코드-경로), [진행 시계와 상태 전환](experiments/research-history.md#시간-진행에서-구별해야-할-대상과-사건), [EX01의좌표 원점](experiments/research-history.md#execute_01--현재-근거로-가능한-판단)을 필요할 때 확인한다. 서로 다른 내부 좌표·실시간ms·녹화프레임을 고정 환산하거나 직접 합산하지 않는다. 성공 영상의 입력점만으로 허용창을 만들거나, 서로 다른 진행 경로의 최솟값·최댓값을 한 창으로 합치지 않는다.

## 새 보스의 실험 운영 — 2026-09-19

베스퍼·기르타블리르·퇴행 변종·쿠사리쿠에서 확인한 **Pre에서 진입 회피, Combo에서 이후 1~n타**와 패턴별 타수는 [공통 해석](boss-control-patterns.md#pre와-combo의-공통-해석--2026-09-21)을 재사용한다. Pre 전체를 한 번의 진입 회피와 동일시하지 않으며, 쿠사리쿠의 Pre 내부 준비 투사체와 진입 대응 구분도 같은 정본을 따른다. **마지막 타 극한 회피·회피지원 → QTE**는 [내부 14개 경로로 확인한 제어스킬 공통 규칙](boss-control-patterns.md#마지막-타-회피와-qte의-공통-해석--2026-09-21)이다. 보스 동작명과 대응 키, 단계 구분과 시간 원점을 구별하며 완료한 해석을 새 controller의 미확인 질문으로 되돌리지 않는다.

환영의 화살 유닛은 literal Pre/Combo 없이 `Attack_09_01`~`_05`를 쓰므로 진입/후속 역할을 재사용한다. 상태별 지원 폭30과 외부 시연은 진입+후속4 후보를 뒷받침하지만, 별도 상태 좌표에서 ms를 계산할 수 없다. 9월22일 수동2·4번에서1타 입력350ms 차이에2·3타 준비 큐 차이는50ms로 관측해 정상 경로의 문구 기준 시간표를 조건부 채택했다. 이후 자동 실험에서 실패 행·선행 조건을 분리하고 기존 성공 교차를 재사용해 구간을 채택했으며, 서비스 반영과 작업 종료를 마쳤다. [환영의 화살 유닛 조사와 최소 관측](experiments/arrow-unit-control-skill.md)을 따른다.

현재 미완료 판단과 담당은 [README](../README.md#현재-단계--2026-09-21), 쿠사리쿠의 관측·조건부 후보·실행 원점은 [보스별 조사](experiments/kusarikku-control-skill.md)를 따른다. 완료한 자료 연결과 실제 성공 폭의 검증을 구별한다.

AI는 외부 영상과 기존 근거로 질문·후보를 좁히고, 실행 설정을 준비·무입력 검증한다. 기존 저장 프로필과 회차 스냅샷에서 확인할 조건을 사용자에게 다시 묻지 않는다. 실험이 필요하면 사용자가 실제 입력·녹화·0/1 결과를 남기고 AI가 기존 records 명령으로 가져와 해석한다. F8 녹화 관측·설정 저장·결과 정정은 현행 실험기를 사용하며 별도 입력 양식이나 설정 생성 체계를 만들지 않는다.

서비스 구간은 현행 미디어의 `windowsMs`와 채택 보고서, 기본 실험 설정은 `tools/experiment/profiles`, 영상 입력 참조는 해당 영상의 `referenceMs`·원본 프레임을 따른다. 이 값들은 역할이 달라 항상 같지 않다. 사용자가 편집한 실행 파일 옆 `profiles`는 다음 실행 설정이며 기본 제공값으로 되돌리지 않는다. 실제 회차 해석은 당시 `ProfileSnapshot`·키·입력 시각·파티·F8 관측을 사용하고, 현재 기본값으로 과거 로그를 다시 해석하거나 덮어쓰지 않는다. 연구 후보는 서비스 영상이 없어도 프로필 무입력 검사 대상이다. 공개한 콘텐츠에만 대응 프로필·대표 영상 연결을 필수로 확인한다.

기르타블리르의 외부 반응에서 최초 후보를 만든 과정과 당시 한계는 [준비 이력](experiments/research-history.md#기르타블리르-최초-후보-준비-이력--2026-09-19)에 보존한다. 현행 실측은 [종료 보고서](experiments/girtablullu-control-skill.md)를 사용한다. 새 보스에서도 로컬 감지 원점·입력과 반응의 연결·파티 분기 중 어느 불확실성이 후보 선택을 바꾸는지 설명하고 필요한 자료만 요청한다. 외부 반응을 실행 기본값으로 복사하지 않으며, 승인받은 미검증 후보 실험과 검증된 성공값을 구별한다.

외부 영상·기존 근거로 후보와 질문을 선택한 뒤 부족한 근거가 서비스 결정을 바꿀 때 실험한다. 자료가 여러 개면 먼저 전체를 간단히 분류해 시작 조건·성공/실패·키 경로·원점 차이를 찾고, 대표·반례·불확실성을 구분할 장면만 정밀 판독한다. 전체를 같은 깊이로 분석하거나 마지막 영상만으로 전체 경로를 대표시키지 않는다. 시작 클릭·문구 출현·감지 원점·준비 전조를 따로 맞춰 시간 차이의 발생 구간을 확인한다.

필요한 실험은 최소 시작 조건 재현 → 전체 기준값 성공 확보 → 묶음으로 이른/늦은 후보 탐색 → 모순이 있는 동작·인접 관계만 분리 → 선택 구간 확인 → 서비스용 대표 영상 확보 순서로 진행한다. 준비 회피부터 결과가 불안정하면 준비를 더 복잡하게 자동화하기 전에 최소 동작·위치·수동 이동 조건을 먼저 좁힌다. 준비 피해는 본 대응 실패와 구별해 기록한다. 기준값은 [중점·50ms 선택 규칙](product.md#초기-구현값과-남은-제품-결정)으로 계산하고 동률을 임의로 올리지 않는다. 이미 수용할 만한 영상이 있으면 수치 통일용 재녹화를 요구하지 않는다. 이미 확보한 근거로 해결된 단계는 반복하지 않는다. 베스퍼의 선행 입력 영향·녹화 지연 방향을 새 보스에 보장하지 않는다. 더 좁은 분해능은 제품 결정에 필요한 반례가 있을 때만 검토한다.

전체 기준 성공은 양끝 실험의 선행 조건이며 사전 비교를 미룰 이유가 아니다. 실제 플레이를 기다리는 동안에도 내부 구간·앞뒤 간격·기존 반례를 적용해 조건부 후보와 탐색 우선순위를 정한다. 정밀 수치를 지지할 근거가 부족하면 정성 비교와 한계·구분 실험을 제시한다.

### 실험 묶음 서식

보스별 보고서 안에서 아래 항목을 채운다. 묶음은 기존 batch에 연결하되 횟수는 남은 질문으로 정한다. 약6회는 사용자의 진행 부담을 나누는 단위이며 의무 횟수나 모든 끝을 한 번에 끝내는 제한이 아니다. 별도 인수인계 문서는 만들지 않는다.

- 대상/조건: 보스 형태·모드·스킬·파티·시작 캐릭터·감지 프로필과 버전.
- 결정할 질문: 결과에 따라 어느 서비스 값이나 다음 행동이 달라지는가.
- 기존 근거: 재사용하는 성공점·실패/예외·영상/로그 ID와 원점.
- 다음 묶음: 고정할 값·변경할 값·순서·녹화 조건. 조건별 표본 수를 임의로 늘려 집계하지 않는다.
- 종료/분기: 채택 근거, 반례가 나오면 분리할 동작, 같은 질문을 계속할 이유.
- 결과: 회차별 동작 성공/실패/미확인/평가제외와 출처, 앞선 실패 이후의 경로 표시.
- 결정/보존: 서비스 채택값과 해석용 추정값을 구분하고, 대표 성공·예외·정렬·서비스 원본의 보존 역할을 적는다.

입력 제출 완료는 게임 성공이 아니다. v3.1.0의 Recording은 OBS 관측 요약이고 이전 버전의 값은 사용자 선택값이다. 실제 상태 정정은 출처·이유와 함께 별도 기록한다. 영상은 여러 파일이어도 되며 한 파일로 합치지 않는다. 누락된 결과를 성공으로 채우지 않는다. 실패 이전의 정상 결과는 살리고 실패 이후는 정상 경로 표본과 분리한다.

**영상 정렬:** 원본 프레임·잘라낸 시작 프레임·실험 원점·기준 입력 표시를 연결한다. 공통 검사는 파일 해시, 구간 순서/폭, 클립 범위, 관측 입력과 기준값의 잔차를 확인한다. 잔차 허용값은 명시적으로 선택하며 베스퍼의2프레임을 다른 콘텐츠의 보편 기준으로 쓰지 않는다. 구간 자체를 늘려 정렬 오류를 숨기지 않는다. 외부 영상에 물리 입력 로그가 없으면 입력 폭 전체를 재검증했다고 주장하지 않는다.

**자료 정리:** 진행 중인 질문에 필요한 원본은 유지하고, 채택·사용자 수용과 확장 범위 종료 뒤 대표·서비스 원본·최종 판단에 필요한 근거만 남긴다. 반복 영상·진단물·상세 로그는 요약에 역할이 옮겨졌으면 제거하며 향후 쓸 수도 있다는 이유로 일괄 보존·압축하지 않는다. 삭제는 확인한 개별 파일과 경로로 한정하고 실제 사용 중인 실행기·설정·원본을 구별한다. records에는 남길 회차만 유지하고 연결을 검증한다. 정본의 과거 경로는 삭제 여부를 명시하며 SHA256을 재생 가능성으로 해석하지 않는다. 현재 보존 목록은 [정리 기록](evidence/experiment-cleanup.json)의 current 한 곳에서 관리한다. 새 보스에서 아직 관측하지 않은 성공률이나 입력 시각은 빈칸으로 유지한다.

제품 동작은 [product.md](product.md)를 따른다. 연구 관측과 로컬 구현에 사용한 가정을 구별해 기록한다.

## 보수적 구간의 대표 교차 조합 확인 — 2026-09-20 합의

최초 탐색에서는 기준 성공 뒤 묶음으로 양끝 후보를 비교하고, 마무리에 이른/늦은 두 방향의 대표 교차 조합을 확인한다. 기존 자료에 같은 조건·시각·키 조합의 성공 근거가 있으면 재사용한다. 혼합 조합의 성공도 그 선행 조건을 붙여 사용하되 독립 단일행 측정이나 모든 조합의 성공 보장으로 바꾸지 않는다. 부족하거나 모순된 동작만 다른 동작을 기준값으로 고정해 분리한다. 개별 끝 탐색과 대표 교차를 각각 새 촬영으로 모두 반복하는 절차가 아니다.

## 판단과 산출물의 평가

역할·검토 시점과 controller 인수 절차는 [AGENTS.md](../AGENTS.md)가 정본이다. 여기서는 그 실행이 원래 목적을 충족했는지 확인하는 방법과 결과의 한계를 다룬다.

### 변경 영향과 실제 산출물 확인

작업은 **결정할 질문 → 그 판단에 필요한 역할·근거 → 적절한 표현·실행 범위 → 결과로 질문에 답할 수 있는지 확인**으로 연결한다. [제품 영역과 영향](product.md#제품-전체의-연결과-변경-판단)은 관련 조건을 찾는 입구다. 영향이 연결됐다는 이유만으로 모든 영역을 구현하지 않는다. 배치 비교에서 공간을 확보한 대표 영역은 영상의 공간 점유 역할을 수행할 수 있지만 실제 전조나 디코딩 지연을 검증하지는 못한다. 반대로 실제 영상이 필요한 질문에서도 전체 제품을 복제할 필요가 있는지는 별도로 판단한다.

비교할 때는 판단에 영향을 주는 조건을 맞추고 장점과 비용을 드러낸다. 생략한 것이 결론을 바꿀 수 있으면 해당 역할을 보완한다. 형상·식별성은 비교물 자체에서, 재생 동기화는 실제 미디어 경로에서 확인하는 등 질문에 맞게 근거를 선택한다. 구현자 검토·기술 검사·사용자 선호·게임 성공·학습 효과를 구별하며 비교 제공을 기본값 채택으로 바꾸지 않는다.

새로운 요구·실패 원인이 드러나면 규칙이나 검사를 추가할 수 있다. 기존 지시의 적용 범위가 잘못됐으면 그 지시부터 고치고 예외 규칙을 겹쳐 우회하지 않는다. 추가 항목은 방지할 실패와 적용 조건을 설명하고, 중복·충돌·역할이 끝난 항목은 통합하거나 제거한다. 지속적인 제품 요구의 회귀 검사는 유지할 수 있으며 임시 비교의 전용 검사는 비교 종료와 함께 정리한다. 규칙 수의 유지나 축소 자체를 성공 기준으로 삼지 않는다.

과거 아이콘 비교에서 필요한 표현을 빠뜨린 실패와 복구 범위를 과도하게 넓힌 실패는 [교정 이력](experiments/research-history.md#비교-범위-교정-이력--2026-09-19)에 보존한다. 해당 실패의 당시 구현 수단을 이후 모든 비교의 의무로 일반화하지 않는다.

### 재개 평가 방법

[사례 질문](../tools/research/judgment-cases.json)은 재개 시 근거 적용을 확인하는 도구다. 다음 작업에 맞는 사례를 골라 정본 문서와 질문을 제공하고, 모범 답안·이전 평가 결과는 응답자에게 주지 않는다. 모든 사례를 매 작업마다 실행하지 않는다. 아래 기준은 답변과 산출물을 평가하는 출발점이며 기준 자체의 적합성도 확인한다.

- 근거를 인용하는 데 그치지 않고 후보·계산·실험 순서에 사용했는가.
- 관측·조건부 예측·서비스 채택, 내부 좌표·입력·화면 반응의 원점을 구별했는가.
- 제안한 환산법을 기존 관측에 실제로 적용하고 반례와 적용 한계를 다뤘는가.
- 추가 자료가 바꿀 결정을 설명하고, 필요 없는 재촬영·정밀 경계 탐색을 자동 요청하지 않았는가.
- 새 조건 사례에서 기존 가설을 기계적으로 반복하지 않고 필요한 부분만 재검토했는가.
- 목적에 필요한 역할을 보존하면서 표현 범위를 선택했는가. 필요한 근거의 누락과 불필요한 재현을 함께 살폈는가. 제품 변경의 영향과 비교/채택 범위를 확인하고 답변의 타당성과 실행 결과를 구별했는가.

질문별 **통과/실패/미확인**, 근거·검토자·제공 문맥·한계를 evidence에 남긴다. 핵심 목적 실패를 평균 점수나 완성도로 덮지 않는다. 구현자의 자기 선언·키워드 포함·앱 검사 통과를 독립 판단 검증으로 세지 않는다. 한 번의 통과는 해당 사례의 결과이며 장기 성능 보증이 아니다.

harness 교정의 효과를 확인할 때는 먼저 기존에 수용·거절된 결과를 사용자 피드백과 대조하여 평가가 과소 구현과 과잉 구현을 구별하는지 점검한다. 과거 피드백에 없는 정답은 확정하지 않는다. 이 확인은 평가 기준의 점검이며 개선 효과 시험을 대신하지 않는다. 이어 같은 자료·권한·모델·비용 조건에서 기존 방식과 교정 후보의 실제 산출물을 비교한다. 가능하면 버전 정보를 가려 평가하고, 목적 충족·중요한 누락·불필요한 확장·사용자 재설명·작업 비용을 확인한다. 설명문이나 서식의 충실도로 산출물을 대체하지 않는다.

개선에 사용하지 않은 조건에서도 확인한다. 같은 대상이라도 배치 비교와 동기화 조사처럼 필요한 역할이 다른 질문, 지적 후 과잉 반대로 바뀌는 후속 응답을 포함할 수 있다. 평가 결과를 보고 교정에 사용한 사례는 더 이상 미사용 평가 사례로 세지 않는다. 개선이 확인되지 않으면 후보를 유지할 이유를 재검토한다. 이는 harness 변경을 평가할 때의 방법이며 매 제품 작업의 의무 절차가 아니다. 현재 수행 범위와 아직 확인하지 못한 부분은 아래 평가 상태를 따른다.

### 외부 조사에서 가져온 설계 근거

장기 에이전트의 진행 상태·검증을 외부에 유지하는 [Anthropic의 운영 사례](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents), 요약 과정의 정보 손실을 다루는 [ACE 연구](https://arxiv.org/abs/2510.04618), 검색뿐 아니라 정보 갱신·다회차 추론을 구분하는 [LongMemEval](https://arxiv.org/abs/2410.10813)을 참고했다. 이들이 이 프로젝트의 원인을 직접 실험한 것은 아니다. 여기서는 기술 재개 성공과 판단 재개 실패가 함께 관측되어 두 검증을 분리한다.

[OpenAI의 harness 사례](https://openai.com/index/harness-engineering/)처럼 짧은 작업 입구와 연결된 정본을 유지하고, [Anthropic의 평가 지침](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents/)처럼 실제 실패를 판단 사례로 바꾼다. 문서나 그래프를 늘리는 것 자체를 해결책으로 간주하지 않는다. 현재 규모에서는 기존 문서 안의 근거·조건·결정 연결을 유지하되, 실제 답변 평가에 더해 변경한 산출물이 질문에 답하는지 검증한다.

추가 조사한 [AGENTS.md 평가 연구 v2](https://arxiv.org/abs/2602.11988v2)는 조사한 저장소·에이전트 조건에서 문맥 파일 제공이 일반적으로 성공률을 개선하지 않았으며 성능 개선 주장을 평가할 것을 권고한다. 이 프로젝트나 현재 모델의 재현 실험은 아니지만 문서 양을 해결책으로 볼 근거는 되지 않는다. [SEI의 Quality Attribute Workshop](https://www.sei.cmu.edu/library/quality-attribute-workshop-collection/)은 목표에서 중요한 품질을 도출하고 시나리오를 구체화하며 품질 간 상호작용을 드러낸다. 여기서는 대규모 워크숍 대신 제품 연결 표와 실제 변경 장면에 적용한다. [Anthropic의 평가 사례](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)는 실행 기록의 주장과 실제 환경의 결과를 구분하고 회귀 사례·능력 평가·사람의 검토를 조합한다. [당시 브라우저 검사](experiments/research-history.md#readme에서-이동한-재개구현-검증-이력)는 그 원칙을 적용한 것이며 특정 harness의 일반 성능이 입증됐다는 뜻은 아니다.
